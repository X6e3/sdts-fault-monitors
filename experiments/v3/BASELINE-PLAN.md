# BASELINES: the v3 trackers against standard set-membership detectors, with the same prior (plan, 2026-11-21)

Status: DRAFT (implementation and DEV tuning come first; the configurations are frozen in a later commit, before any
run on the comparison block)

Author: Can Koç. Written 2026-11-21 on branch `sdts-v3/template-state`.

## 0. Why

An independent review of `df40c058` named the missing equal-budget comparison as the main weak point: v3 has been
measured against v2 only, so how much of F3's gain comes from its architecture is not known. `RELATED-WORK-NOTES.md`
section 3 lists the baselines a reviewer will expect. This study runs them on the same data, with the same prior and
the same decision semantics, against the same certified oracle.

**Decided 2026-11-21:** the comparison block is freeze 3's validation block; all five baselines B1–B5.

## 1. Data

- **Comparison block:** 440400–440599, freeze 3's validation block (9600 runs: the MANIFEST-V3 design). Its oracle
  (t\*, status) and v2 are recorded in `results/v3/freeze3/validation-440400-440599-948b46b0/rows.jsonl`; F3's
  detections too. The block is not used to judge F3 again (FREEZE-V3 section 6); it is the common ground on which
  the baselines are measured. No baseline sees it before its configuration is frozen.
- **Identity:** the runs are regenerated by `dev_scenarios.run`. Before anything is scored, v2 is recomputed on 48
  runs (one per design cell, the smallest sha256 keys) and must equal the recorded v2 detection on each.
- **Tuning data:** DEV only, MCU-2E's 1400 rows (430000–430029 comparison rows and 430070–430089 edge rows).

## 2. The common prior

Every method gets exactly the assumptions of FREEZE-V3 section 1:
- the model: the exact recurrence of `thermal.py` (DIAG-3 amendment 9), its matrix rounded once;
- the noise bound δ + η (η = 1e-9 °C, the data allowance of F3);
- the ambient rate ρ_A and the box TA ∈ [23, 27] °C, with the implied boxes of ac and as;
- the start: the P0 steady state, the segment {t (1, 1, 1)};
- the reachable-set bounds of Lemma 2 (V3_NOTES section 4), which follow from the model and (b)–(c): in the four
  error-plane directions ac − TA, as − TA, ac − as and the as-velocity v. Given to B1–B3 as constraints or virtual
  strips; whether a method uses them is a tuning option (`box` or `box+err`), because an outer intersection with a
  thin strip can widen the set in other directions. B4 (intervals) can use the boxes only.

The decision is the same for all: an alarm at the first sample at which the method proves that no admissible
explanation exists.

## 3. Methods

| | method | budget parameter | grid (DEV tuning) | fault decision |
|---|---|---|---|---|
| cyl16p | v3 template state (freeze 1), LP-free | 42 supports | fixed | as-range misses the slab |
| F3 | v3 window tracker (freeze 3) | W = 256, K = 64 | fixed (recorded) | certified alarm |
| B1 | constrained zonotope CZ (Scott et al. 2016) | constraints n_c, order o | (n_c, o) ∈ {(2, 1), (1, 2), (3, 1)} (within M1) and n_c ∈ {4, 16, 64} × o ∈ {2, 8}, policy fifo, prior box or box+err; and (8, 4) greedy; Scott's LP rescaling for (8, 4) on a fixed 200-row DEV subset, reported only (it costs 15–20 times more) | LP range test of x_2 (Scott, Prop. 2) |
| B2 | strip-intersection zonotope (Alamo, Bravo, Camacho 2005), F-radius weight | order o | o ∈ {2, 4, 8, 16, 32}; prior box or box+err | strip test |
| B3 | zonotopic observer, constant gain (Combastel 2015) | order o, weight q | o ∈ {2, 4, 8, 16, 32}, q ∈ {1e-2, 1, 1e2, 1e4}; prior box or box+err | residual-set test |
| B4 | interval observer (cooperative form) | gain L | L = (a·M₁₂, b·M₂₂, c), a ∈ {0, ½, 1}, b ∈ {0, ¼, ½, ¾, 1}, c ∈ {0, −0.01, −0.05}: A − L C ≥ 0 (the boxes keep the TA mode bounded) | output-interval test |
| B5 | forward-only window: F3 with the smoothing fold off | W = 256, K = 64 | fixed (F3's) | certified alarm |

- B1–B3 get the TA box and the implied ac, as boxes as intersections (B1) or virtual strips (B2, B3) at every
  sample, so that their prior equals ours. Their reductions are the published ones (B1: Scott et al. section 4;
  B2, B3: Girard's reduction).
- B5 is F3's code with the fold's information horizon set to the window base instead of the current sample (the
  `smooth` switch of the DIAG-3 window); everything else (certificates, cap, failsafe) is F3's. It isolates the gain
  of the smoothing fold.
- B3 uses a constant gain, the steady-state Kalman gain for weights Q = q ρ² e3 e3′ and R = (δ + η)². With the gain
  re-optimized at every sample for the F-radius it would equal B2 (Combastel's own result), so the constant gain is
  the distinct, cheaper variant.
- B1's complexity control (`baselines_cz.py`): rescaling by interval propagation; constraint elimination (an exact
  one first, else the oldest constraint (`fifo`) or the globally cheapest (`greedy`)); Girard's reduction on the
  lifted zonotope. Every step is an outer approximation.
- B1–B4 run in plain binary64 as published, without outward rounding. An alarm they raise on an admissible run or
  before t\* is reported as a soundness finding of that implementation.

**Tuning rule (DEV):** for each baseline and each memory budget below, the configuration with the smallest DEV paired
lag among those with no alarm on an admissible DEV run and none before t\*. The chosen configurations are committed
before the block run.

## 4. Budgets

Memory is counted in stored reals of the state (tables and code excluded):
- cyl16p: 42 (+ S, 2 doubles, common to all methods);
- F3: up to 65 measurements, the 42 start supports, and its LP (at most 445 rows and 679 variables on the block);
- B1: 3 + 3·(3o) + n_c·(3o + 1) (centre, generators, constraints); B2, B3: 3 + 3·(3o); B4: 6.

Two budget points are reported: **M1 ≈ 42 reals** (cyl16p's) and **M2 = F3's**, and each baseline's whole
memory–lag curve over its grid. Time: CPU seconds per sample on Arch, single core, and LPs per sample.

## 5. Measures

As freeze 3's scoring: paired lag against v2 (D_paired) over the events v2 detects; misses among the certified
events; detections exactly at t\*; soundness findings (alarms on admissible runs, before t\*); CPU time; memory.

## 6. Hypotheses (fixed now; each judged by a seed-bootstrap 95 % interval of the paired-lag difference, 200 seeds)

- **H-B1 (MCU budget):** at M1, cyl16p's paired lag is below each of B1–B4's chosen configuration.
- **H-B2 (the smoothing fold):** F3's paired lag is below B5's.
- **H-B3 (best baseline):** at M2, F3's paired lag is below B1's chosen configuration.

For each: **supported** if the interval of (ours − baseline) lies below 0; **refuted** if it lies above 0;
**not resolved** otherwise. Reported as they come out.

## 7. Order of operations

1. Implement B1–B5 (`diag/baselines.py`), with unit checks on DEV runs (each baseline's set contains the true state
   on healthy runs; B5 equals F3 on a run with no fold).
2. DEV tuning (1400 rows); choose the configurations by the rule of section 3; commit them (status: FROZEN).
3. The block run on Arch (size and duration stated to Can before it starts), then the identity check, then scoring.
4. A dated record with every result as it comes.

## 8. What this can show, and what it cannot

- **Can show:** where v3 stands against the standard families at equal prior and budget, on 9600 runs with a
  certified reference.
- **Cannot show:** anything on another plant, under model mismatch, or with priors the baselines would choose
  differently in practice (for example without the ambient box).
