# C1 on the used validation blocks (plan, 2026-11-24)

Written and committed before any result of it. Approved by Can Koç on 2026-11-24 ("tamam adamım dediğin gibi olsun",
for option A: the revised C state beside the frozen one on the two used validation blocks, nothing on fresh seeds).

## Why

The paper says the revised C state (c1, `C1-PLAN.md`, accepted on DEV in MCU-NOTES 2h) "is not validated on fresh
seeds". It was made after validation 1's results were known, so no block can validate it now except a fresh one;
that is a separate decision (seeds 440600–440999 are the last two fresh blocks) and is not taken here. What can be
checked without new seeds: whether c1 raises the same alarms as the frozen C state on the runs of validations 1 and 3.
On validation 1 the frozen C float64 build equals the validated Python template on all 9,600 runs
(RECORD-2026-11-18-validation.md, verdicts; rechecked from its rows on 2026-11-24: 9,600 of 9,600). If c1 equals the
frozen C state there, validation 1's scores of the template are c1's as well.

## What runs

- `mcu/esp32/c1_val_compare.py`, on Arch, from a clean clone at this plan's commit: the PC builds of the frozen C
  state and of c1 (both float64), `host_trace` as built for MCU-2E and C1 (GCC, `-ffp-contract=off -fno-fast-math`):
  frozen `~/Research/sdts-mcu-avr/out/esp32-cyl16p-double/host_trace`, sha256 `aa581fb2d783409352cbeec59409e27f656a9a9cc90d667954b40b66103d89cf`;
  c1 `~/Research/sdts-mcu-avr/out/esp32-c1-b68f865d/host_trace`, sha256 `5d4fddeea11b3aa842e4101d16e843bf7a730443b99158ad3022ce12d9afff95`.
  The script refuses binaries with other hashes.
- Rows: every run of validation 1 (seeds 440000–440199, `results/v3/freeze1/validation-440000-440199/rows.jsonl`) and of
  validation 3 (seeds 440400–440599, `results/v3/freeze3/validation-440400-440599-948b46b0/rows.jsonl`), 19,200 in all.
  The data are regenerated by `dev_scenarios.run` after `unlock_validation` with each block's approved manifest sha256
  (as the baseline comparisons did on validation 3). No oracle runs: t*, status and IM's detection are the rows'.
- Per run: the first flagged sample of each build and the number of samples.

## Checks (fixed now)

- **U1** complete: 9,600 runs per block, each with 3,600 samples.
- **U2** c1 is never earlier than the frozen C state (C1-PLAN Y4: an earlier c1 flag would be a bug).
- **U3** the first flagged sample of c1 equals the frozen C state's on every run.
- **U4** on validation 1, the frozen C state's first flagged sample here equals the recorded `c.cyl16p_double` on every
  run (the regenerated data and this build reproduce the validation's own C build).
- **U5** c1 raises no alarm on an admissible run (healthy, or certified with no t*), edge noise included.

Reported either way: c1 against the Python template (validation 1: `candidates.cyl16p`; validation 3: the first
comparison's `cyl16p`, `results/v3/baselines/block-9438dffa/rows.jsonl.gz`), and c1's paired lag, D_paired against IM
and misses on each block, by the scorer's rules (paired events: certified t* and IM detects; a miss at 3,600).

**Verdict:** SAME ALARMS if U1–U5 hold; DIFFERENT, with every differing run listed, otherwise (a run where c1 is later
is a cost of its wider slab, as in C1-PLAN; an earlier one is a bug); INCOMPLETE if runs are missing.

## What it shows, and what it does not

- **Shows:** on two used blocks, whether c1's alarms are the frozen state's, and so whether the validated scores
  carry over to the C state that is sound for |v| ≤ δ by construction.
- **Does not show:** a validation of c1 (both blocks were seen before c1 existed); anything on the boards (the ESP32
  and the Uno were checked on DEV in MCU-NOTES 2h).
