# H-FB: F3's solver-failure path on fresh seeds, under injected failures (plan, 2026-11-21)

Status: DRAFT, not approved

Author: Can Koç. Written 2026-11-21 on branch `sdts-v3/template-state`. Nothing in this plan is generated before the
status line above says APPROVED, in a commit that changes only that line.

## 0. Why, and what this is not

Freeze 3 passed (`RECORD-2026-11-21-validation.md`), but on its block no LP of F3 failed all its attempts: the
solver-failure path, which is what F3 adds to F, never ran. Its soundness rests on the written proof and on DEV
tests with injected failures (DIAG-3 amendment 10: R2, R3, U5, U5b). This test runs the same injections on data
nobody has seen.

- It is **not** a second look at freeze 3's hypothesis H-F3. That verdict stands as recorded, and
  `FREEZE-V3.md` section 6 forbids judging the same candidate on another block. H-FB is a different hypothesis:
  robustness of the implementation under failures injected at fixed rates.
- It uses **neither DEV nor validation seeds**. The seeds are generated in a namespace of their own (section 2).
  The reserved block 440600–440999 stays untouched.
- The injection rates are DEV's (amendment 10), chosen to reach every path. They are not a model of real failure
  rates, and the injected statuses (2 and 4) are not real HiGHS failures.

**Decided 2026-11-21:** a new seed namespace instead of the reserved block; 25 seeds; the exact audit on the Mac.

## 1. Hypothesis

**H-FB.** The frozen F3 (`MANIFEST-V3.json`, checked before anything runs), with LP failures injected by
amendment 10's harness at its settings a–f, on the 1200 runs of section 2:
- raises no alarm on an admissible run and none before the oracle's certified t\*;
- certifies every alarm it raises (a finite, negative certified margin);
- keeps at most K_cap + 1 = 65 measurements;
- counts every failed LP in its failsafe counters exactly as the harness logs it, role by role;
- has no empty-slab failure;
- and, in the exact rational audit of settings b and e (variant F3a), no bound it uses is violated.

The same holds without injection (setting none), which is also the reference for the reported costs.

## 2. Data

- **Namespace** `v3fb`, seeds **450000–450024** (25). Generated by `dev_scenarios.run` with only the seed string's
  prefix changed (`fb_run.py`; `dev_scenarios.py` itself is not changed). Never generated before this test.
- **Design per seed:** freeze 3's (MANIFEST-V3): 11 cells × E0, E1 × rw, ramp with uniform noise, plus healthy ×
  E0, E1 × rw, ramp with edge noise. 48 runs a seed, **1200 runs**.
- **The oracle** (certified t\* and status) and v2 are computed once per run, as in the validation runner.

## 3. Runs

| setting | what fails (amendment 10, unchanged) | where |
|---|---|---|
| none | nothing injected | Arch |
| a | 1 % of fold-direction LPs | Arch |
| b | 10 % of fold-direction LPs | Arch; and F3a on the Mac |
| c | 1 % of as-range and 1 % of certificate LPs | Arch |
| d | every direction of every fourth fold (full resets) | Arch |
| e | 10 % of fold-direction LPs and every P_J LP (the a priori path) | Arch; and F3a on the Mac |
| f | every upper-side certificate LP | Arch |

- The harness's choices are a hash of (row key, t, role, direction or side, setting); half status 2, half status 4.
  The row keys are `fb-SEED-CELL-ARM-AMBIENT-NOISE`.
- Arch: `fb_run.py` from a clean clone at the approval commit, 13 workers at nice 19 (the ESP32 run of MCU-2E may
  still be using the serial port; it needs almost no CPU). Mac: a clean worktree at the same commit, 8 workers.

## 4. Decision (fixed)

Per setting (none, a–f, variant F3):
- **C1** complete: a record for every one of the 1200 runs.
- **C2** no alarm on an admissible run: every healthy run, and every fault run the oracle certified consistent.
- **C3** no alarm before the oracle's certified t\*.
- **C4** every alarm certified: certified, with a finite, negative certified margin.
- **C5** at most 65 measurements kept.
- **C6** the failsafe counters equal the harness's log, role by role, on every run.
- **C7** no empty-slab failure.

Across a–f:
- **C8** every fallback path reached at least once: fold-direction, P_J-a-priori, as-range and certificate
  failures with status 2 and with status 4; one-side and both-side as-range fallbacks; full resets; implied bounds;
  measurements not kept. (Amendment 10's U2 list.)

Mac, variant F3a, settings b and e:
- **C9** complete, at least one implied bound audited in all, and no violation in the exact audit.

**Verdict:**
- **FAIL** if C2–C7 fail on any complete setting, or C9 on a complete audit.
- Otherwise **INCOMPLETE** if a setting or an audit is incomplete.
- Otherwise **INCONCLUSIVE** if C8 or C9 does not hold: a path was not reached.
- Otherwise **PASS**.

`fb_run.py verdict` applies this order.

## 5. Reported, not deciding

Per setting, against setting none: detections that differ, detections earlier than none (FREEZE-V3 section 1:
a fallback can change which measurements the cap keeps), misses, D_paired against v2, detections after a full reset
(d), box-proved alarms, CPU time. The oracle's undetermined runs and its solver crashes, as in the validation
records.

## 6. Order of operations

1. **This plan**, committed with `fb_run.py`.
2. **Rehearsal** on Arch, from a clean clone of the plan commit (DEV rows only; no `v3fb` seed is generated):
   `fb_run.py identity` for settings b, d and f on 6 DEV rows each: the 6 keys with the smallest sha256, a fixed
   choice that spreads over cells. Each record must equal amendment 10's R2 record of the same row in every field
   but wall-clock time. The oracle stage's job must give the DEV rows' t\*, status and v2 on two of them, one with
   a certified t\* and one healthy. Any difference stops the test; it is recorded and the plan is revised.
   (A first rehearsal at `7fb68b64` picked the first 6 rows, all healthy; it passed, and the choice was changed
   so that fault rows and certificates are reached.)
   **Rehearsal result** (2026-11-21, Arch, clean clone of `626fb2ec`, 12 workers at nice 19; outputs in
   `results/v3/fb/rehearsal-626fb2ec/`): **passes.** All 18 records (b, d and f on the same 6 rows: two jump_0.5,
   gain_0.01, drift_0.001, drift_0.02, healthy) equal amendment 10's R2 records in every field but wall-clock time.
   The injections reached fold failures (b: 1853, d: 4536) and upper-certificate failures (f: 400), each about
   half status 2, half status 4. The oracle job gave the DEV rows' t\*, status and v2 on 430019 jump_0.5 E0 ramp
   (t\* 382) and 430014 healthy E0 ramp (certified consistent).
3. **Approval:** the status line becomes `Status: APPROVED by Can Koç on YYYY-MM-DD` in a commit that changes
   nothing else.
4. **Runs:** `fb_run.py oracle OUT`, then `fb_run.py run OUT --setting S` for none and a–f on Arch, and
   `--variant F3a` for b and e on the Mac (with the Arch `oracle.jsonl`, sha256 checked).
5. **Scores:** `fb_run.py summary` for each run directory, then `fb_run.py verdict OUT`.
6. **A dated record** with the verdict as it comes out.
7. **Infrastructure failure** (a crash, a reboot): the identical command again. Finished runs are kept (one file
   per run), so it resumes. No rerun for any other reason.

## 7. What a PASS shows, and what it does not

- **Shows:** on fresh data, every fallback path of the frozen F3 keeps the run sound, certified, within memory and
  correctly counted under these injections, and the exact audit finds no violated bound in b and e.
- **Does not show:** how often a real solver fails; that a real failure looks like an injected status; the cost of
  a fallback at real rates; anything about an MCU, float32, a real plant or model mismatch (`FREEZE-V3.md`
  section 7).
